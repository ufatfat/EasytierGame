## 1. 概述

EasyTier Game 让玩家输入同一个房间名和密码，就能和朋友进入同一个虚拟局域网，然后用游戏自带的“局域网联机”一起玩。它附带最新的 EasyTier 内核，提供一键启动、成员状态查看、内核管理和一组排障工具，支持 Windows 和 macOS。

这一版要解决三件事：主界面拥挤、入口分散；“找人一起玩”只能靠群里传房间名；协调服务用一把共用密钥，无法管理具体的人。

## 2. 现状与问题

| 问题 | 表现 | 影响 |
|---|---|---|
| 主窗口过小 | 主窗口 340×340，服务器、房间、IP、开关、十几个按钮挤在一屏 | 新用户找不到主操作，误点高级功能 |
| 入口分散 | 房间信息、日志、高级选项、增强工具、分享导入分布在按钮、下拉菜单和链接里 | 功能可发现性差，同类操作位置不一致 |
| 联机状态不显眼 | “联机成功”只是一个小标签，虚拟 IP 藏在输入框里 | 用户不确定是否连上，排障时找不到自己的 IP |
| 找人只能靠群聊 | 房间名、密码、服务器地址都要手动复制粘贴 | 开黑门槛高，填错一项就连不上 |
| 协调服务共用一把密钥 | 所有客户端持有同一个 `SERVICE_TOKEN`，主机名自填 | 泄露只能全员换密钥；可无限新建身份刷光 IP 池；可冒充他人发公告 |

## 3. 目标与非目标

### 目标

- 新用户从打开应用到联机成功，只需要填房间名并点一次“启动联机”。
- 联机状态、虚拟 IP、成员连接质量一眼可见。
- 玩家不离开应用就能找到公开房间并一键加入。
- 协调服务能按人发放、吊销密钥，有管理员处理冲突和违规内容。
- 深色、浅色两套主题，跟随系统或手动切换。

### 非目标

- 不做账号注册、登录和第三方 OAuth；身份仍由管理员发放的密钥决定。
- 不做语音和文字聊天，大厅只提供外部联系方式的说明栏。
- 不改变 EasyTier 内核的组网协议，也不由协调服务创建或托管中转节点。
- 不提供移动端客户端。

## 4. 用户与场景

| 角色 | 描述 | 核心诉求 |
|---|---|---|
| 普通玩家 | 想和朋友玩支持局域网联机的游戏，如《怪物猎人：世界》《深岩银河》《无主之地 3》 | 填最少的东西，马上连上；连不上时知道为什么 |
| 房主 | 组织一局游戏、发房间信息的人 | 让别人方便地加进来，满员或结束后不用手动通知 |
| 社群管理员 | 运营 QQ 群或社区、部署协调服务的人 | 给成员发密钥，踢掉捣乱的人，处理 IP 冲突 |
| 进阶用户 | 会自建服务器、用子网代理、写配置文件 | 高级功能完整，不被简化掉 |

### 关键场景

1. **熟人开黑**：房主在群里说“今晚 9 点怪猎”，大家打开应用，从大厅点“加入”，输入群里给的密码，进游戏。
2. **连不上排障**：成员在房间信息里看到自己是“中转”且延迟 180ms，按增强工具里的 1–5 步检查广播、网卡跃点、防火墙。
3. **社群治理**：有人刷公告，管理员在成员管理里吊销他的密钥，他登记的 IP 自动释放。

## 7. 成员与权限

🟡 已实现。协调服务从“一把共用密钥”改为“每人一把密钥 + 管理员”。代码在分支 `claude/coordinator-member-keys`，服务端 9 个测试和客户端 3 个测试通过。

### 身份模型

- **成员**：由管理员创建，名字由管理员设定，持有一把 `etk_` 开头的个人访问密钥。服务端只保存密钥的 SHA-256。
- **设备**：每台客户端本地生成的随机令牌，用于区分同一成员的多台设备的 IP 登记。
- **角色**：成员、管理员两种。

### 需求

| 编号 | 需求 | 优先级 |
|---|---|---|
| MEM-01 | 首个管理员只能在服务器上通过命令行创建：`node service/server.mjs member add <名字> --admin`；命令行同时支持 list、reset-key、revoke，作为密钥丢失后的恢复手段 | P0 |
| MEM-02 | 管理员在客户端新建成员，新密钥只显示一次并提供复制按钮 | P0 |
| MEM-03 | 管理员可重置任意成员的密钥，旧密钥立即失效；重置自己的密钥时客户端自动替换为新密钥 | P0 |
| MEM-04 | 管理员可吊销成员：密钥立即失效，其登记的 IP 释放，公告保留；吊销后可重新创建同名成员 | P0 |
| MEM-05 | 管理员可调整他人角色，不能修改自己的角色或吊销自己 | P0 |
| MEM-06 | 管理员可释放任意 IP、删除任意公告；普通成员只能撤回自己的公告 | P0 |
| MEM-07 | 公告和 IP 登记显示管理员设定的成员名，自填主机名放在括号里 | P0 |
| MEM-08 | 每位成员最多给 `CLAIMS_PER_MEMBER` 台设备登记 IP（默认 3）；一台设备的登记不能被其他成员的密钥接管 | P0 |
| MEM-09 | 旧数据库启动时自动补字段；旧数据显示为“未归属”，旧公告仅管理员可删 | P1 |
| MEM-10 | 成员列表显示最近使用时间、登记 IP 数、公告数 | P1 |

### 接口

```text
GET    /v1/state                    当前身份 me、IP 登记、公告
PUT    /v1/claim                    登记或更换本设备 IP
DELETE /v1/claim                    释放本设备 IP
POST   /v1/announcements            发布公告
DELETE /v1/announcements/:id        撤回自己的公告（管理员可删任意公告）
GET    /v1/admin/members            成员列表                       仅管理员
POST   /v1/admin/members            新建成员，返回一次性密钥         仅管理员
POST   /v1/admin/members/:id/key    重置密钥                       仅管理员
PATCH  /v1/admin/members/:id        修改角色                       仅管理员
DELETE /v1/admin/members/:id        吊销                           仅管理员
DELETE /v1/admin/claims/:ip         释放任意 IP                    仅管理员
```

### 验收标准

- [ ] 错误、伪造或已吊销的密钥返回 401，普通成员调用管理接口返回 403。
- [ ] 重置密钥后旧密钥下一次请求即失败。
- [ ] 吊销成员后，其所有 IP 登记从列表消失。
- [ ] 任何接口的响应都不包含密钥或密钥哈希。
- [ ] 客户端只把请求发往 HTTPS 或本机地址，不跟随重定向，只能调用上表列出的接口。

## 8. 房间大厅

🟣 设计完成。大厅建在协调服务上，与全局 IP、公告共用服务地址和个人密钥。玩家可以浏览别人发布的公开房间并一键加入，也可以把自己正在联机的房间发布上去。

### 主流程

1. 房主联机成功后，在大厅点“发布我的房间”。
2. 填标题、选游戏、设人数上限和标签；服务器和房间名自动带出。
3. 其他玩家在大厅按游戏筛选，看到人数、延迟、是否要密码。
4. 点“加入”，确认替换哪些配置，输入密码。
5. “加入并启动联机”，自动填入并连接。

### 需求

| 编号 | 需求 | 优先级 |
|---|---|---|
| LOBBY-01 | 大厅列表显示：游戏封面、标题、游戏名、房主（成员名）、发布时间、标签、人数与上限、是否需要密码、预计延迟；已满房间置灰且不可加入 | P0 |
| LOBBY-02 | 支持搜索标题、游戏和房主；按游戏筛选；“只看有空位”；排序支持延迟最低、最新发布、人数最多 | P0 |
| LOBBY-03 | 只有联机成功的客户端才能发布；服务器地址和房间名取自当前配置，不可手改，避免发布和实际不一致 | P0 |
| LOBBY-04 | 密码有两种模式：“加入时询问”（服务端不保存密码，加入者手动输入）和“直接公开”（加入时自动填入）；默认为“加入时询问” | P0 |
| LOBBY-05 | 加入前弹出确认，说明将替换服务器、房间名、密码，保留成员名和 IP 模式；若正在联机，先停止当前联机 | P0 |
| LOBBY-06 | 房主客户端每 30 秒发送心跳并上报在线人数；超过 90 秒没有心跳的房间自动下架；停止联机时立即下架（默认开启，可关） | P0 |
| LOBBY-07 | 房主可编辑、下架自己的房间；管理员可下架任意房间 | P0 |
| LOBBY-08 | 每位成员同时最多发布 1 个房间；标题不超过 24 字，说明不超过 200 字，标签最多 5 个 | P1 |
| LOBBY-09 | 预计延迟由客户端测量到房间服务器的连接耗时，不由房主上报 | P1 |
| LOBBY-10 | 满员后可选择自动隐藏；加入时可同时保存为房间配置 | P2 |
| LOBBY-11 | 主界面未联机时，状态卡提供“去大厅找人一起玩”的入口 | P2 |

### 接口草案

```text
GET    /v1/rooms                    房间列表（支持 game、has_slot 参数）
POST   /v1/rooms                    发布房间（每位成员最多 1 个）
PATCH  /v1/rooms/:id                编辑标题、标签、说明、人数上限
PUT    /v1/rooms/:id/heartbeat      心跳，上报在线人数
DELETE /v1/rooms/:id                下架（房主或管理员）
GET    /v1/rooms/:id/connection     获取联机信息；公开密码模式下包含密码
```

### 房间数据

| 字段 | 说明 |
|---|---|
| `id`, `member_id` | 房间 ID；房主成员 ID，名字从成员表读取 |
| `title`, `game`, `tags`, `description` | 展示信息；game 为游戏名文本 |
| `capacity`, `member_count` | 人数上限；房主心跳上报的在线人数 |
| `servers`, `network_name` | 服务器地址列表与房间名，取自房主当前配置 |
| `password_mode`, `password` | `ask` 时不存密码；`public` 时保存密码，仅通过 connection 接口返回 |
| `created_at`, `heartbeat_at` | 发布时间；最后心跳时间，用于过期下架 |

### 验收标准

- [ ] 房主停止联机后，其他客户端在下一次刷新（不超过 15 秒）时看不到该房间。
- [ ] 房主客户端异常退出，90 秒后房间自动下架。
- [ ] “加入时询问”模式下，服务端数据库和任何接口响应里都没有房间密码。
- [ ] 从点击“加入”到开始联机，用户最多需要输入一次密码。
- [ ] 被吊销成员发布的房间立即下架。

## 9. 非功能需求

| 类别 | 要求 |
|---|---|
| 安全 | 密钥只存哈希；客户端只连 HTTPS 或本机，不跟随重定向，接口白名单；请求体上限 16KB，响应上限 2MB；生产环境在反向代理上做 HTTPS 和限速 |
| 隐私 | 协调服务配置和客户端身份只存在本机，不进入房间分享码和 config.json；大厅默认不公开房间密码 |
| 可靠性 | 登记模式下协调服务不可达时阻止启动，避免误用过期 IP；IP 登记变更为单条原子语句，冲突时保留原登记 |
| 性能 | 社区和大厅面板打开后 15 秒刷新一次；单次请求超时 10 秒；协调服务使用内置 SQLite，单机即可承载一个社群 |
| 兼容性 | Windows x64、macOS Apple Silicon 与 Intel；Windows 专属工具在 macOS 上隐藏；旧版协调服务数据库可直接升级 |
| 可运维 | 协调服务为单个 Node.js 24 进程，无第三方运行依赖；命令行可在不停服时管理成员 |

## 10. 成功指标

以下目标值为建议，上线前需要确认数据采集方式。客户端目前没有遥测，协调服务侧的指标可以从数据库统计。

| 指标 | 定义 | 建议目标 | 数据来源 |
|---|---|---|---|
| 首次联机耗时 | 首次打开到首次联机成功的时长 | 中位数 < 2 分钟 | 需新增本地统计 |
| 大厅加入转化率 | 点“加入”后成功联机的比例 | > 80% | 协调服务 |
| 大厅使用率 | 周活成员中发布或加入过大厅房间的比例 | > 30% | 协调服务 |
| 密钥轮换处理时长 | 管理员从发现问题到吊销完成 | < 1 分钟 | 操作流程 |
| 直连比例 | 房间成员中直连而非中转的比例 | 观察项 | 需新增本地统计 |

## 11. 里程碑

| 阶段 | 内容 | 前置条件 |
|---|---|---|
| M1 跨平台与社区 | 合并 macOS 支持、全局 IP 登记与公告 | 当前跨平台分支提交 |
| M2 成员与权限 | 合并 `claude/coordinator-member-keys`；更新部署文档，给现有用户发放个人密钥 | M1 |
| M3 界面改版 | 新主窗口、底部入口栏、停靠面板、深浅主题 | 与 M2 并行 |
| M4 房间大厅 | 协调服务房间接口与心跳；大厅、发布、加入三个界面 | M2（依赖成员身份）、M3（依赖入口栏） |

## 12. 风险与待决问题

### 风险

- **升级中断**：M2 上线后旧的共用密钥全部失效。需要管理员提前用命令行创建账号并分发密钥，文档里写清楚迁移步骤。
- **大厅信息过期**：心跳依赖房主客户端在线，网络抖动可能导致房间被误下架。心跳超时取 3 倍间隔，并在房主端提示“已从大厅下架，可重新发布”。
- **服务端无限速**：协调服务本身不限速，依赖反向代理。社群自行部署时可能漏配。
- **主窗口尺寸变化**：从 340×340 变为 400×720，小屏笔记本上可能需要滚动，需验证 768 像素高的屏幕。

### 待决问题

- [ ] 大厅是否需要“申请加入、房主审批”模式，还是密码已足够？
- [ ] 游戏名是自由文本，还是维护一份内置游戏列表以便筛选和显示封面？
- [ ] 是否允许一个协调服务开启多个相互隔离的大厅（例如按社群分组）？
- [ ] 成员是否可以自助重置自己的密钥，还是必须由管理员操作？
- [ ] 是否在服务端内置简单的按成员限速，而不完全依赖反向代理？
